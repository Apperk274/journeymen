# Journeymen

Minecraft **1.21.1** mod for **NeoForge and Fabric**, built from MultiLoader-Template. Mod ID `journeymen`, package `io.github.apperk274.journeymen`. The owner plays a 1.21.1 modpack and wants the mod to work in it, so we stay on 1.21.1.

## Commands

Always run Gradle through mise. There is no global `JAVA_HOME`, and Java 21 comes from `mise.toml`.

```sh
mise exec -- ./gradlew build
mise exec -- ./gradlew :neoforge:runClient
mise exec -- ./gradlew :fabric:runClient
mise exec -- ./gradlew :neoforge:runData
```

## Testing

Test headlessly with the tools in `testing/`; **read `testing/README.md` before writing or running tests** (scripts, command-file syntax, waits, fail patterns, suites, debug commands, client screenshot hooks, TFC details). From PowerShell in the repo root:

```powershell
testing\server_test.ps1 -Loader neoforge|fabric|tfc -CommandsFile test_hang.txt[,…]   # suites against one dev server over RCON
testing\run_regress.ps1 -Loaders neoforge                                             # full regression for one loader
testing\smoke.ps1 -Loader fabric                                                      # dev client starts without crashing
```

- Never use real-time `sleep` in test or investigation command files (the harness rejects it). Use the sprinting waits (`ticks`, `waitlog`, `waitfor`) so the server runs as fast as it can; use `nosprint` or `realsleep` only when real time is genuinely needed, and say why in your report.
- While working on a change, run only the relevant suite on one loader. Run the full regression on all loaders (NeoForge, Fabric, TFC) once at the end.
- Never chain several server runs in one shell command that could exceed the tool's 10-minute limit; run them as separate commands (e.g. `run_regress.ps1` once per loader).
- Stop every background process, watcher, server and client you start before finishing, kill leftover dev `java.exe`, and leave RCON off. `server_test.ps1` turns RCON on and restores `server.properties` itself.
- Each command file sets up and force-loads its own area and doesn't rely on another file's leftovers. Commands that need a player run through the dev-only `/journeymen debug as`; screen buttons and clicks through `debug action`, `debug use`, `debug interact` and `debug gamemode`.
- To reproduce something from the owner's save, copy it into the run dir and point `level-name` at the copy. Never run the original.

### TerraFirmaCraft

The owner's modpack is TerraFirma Rebirth 2 (NeoForge 21.1.248, TFC 4.2.9 and many addons), so changes are also tested with TFC. `mise exec -- ./gradlew :neoforge:syncTfcMods [-Ptfc_instance=<path>]` copies the jars in `neoforge/tfc-test-mods.txt` from the CurseForge instance into `neoforge/run-tfc/mods`; `:neoforge:runTfcServer` / `runTfcClient` (loader `tfc` in the scripts) use that run dir. TFC is NeoForge-only, so Fabric only has to keep working without it. TFC caps stack sizes (dirt to 32), the pack unifies emeralds, buckets and metals into TFC items, TFC soils are `tfc:dirt|grass|farmland|grass_path/<soil>`, TFC storage (barrels, large vessels) has only a NeoForge item handler, and mining raw rock can start cave-ins that also take vanilla stone, so TFC test areas use a `minecraft:smooth_stone` floor.

## Architecture rules

- Put as much as possible in `common/`. It sees only vanilla Minecraft (Mojang mappings + Parchment), so no NeoForge or Fabric imports.
- Loader-specific code goes in `neoforge/` or `fabric/`: registration, entity renderer registration, commands registration, networking, menu types, config. Expose it to common through an interface in `common/.../platform/services` with a `META-INF/services` entry in each loader.
- Every feature has to work on both loaders.
- Other mods are reached through loader APIs, never through their classes: storage through NeoForge's item handler capability and Fabric's Transfer API, fluid containers through NeoForge's `FluidUtil` and Fabric's fluid storage, hoes and shovels through NeoForge item abilities (`ICompatHelper`). Rules about blocks come from the game itself (loot tables, tool actions, block states), not from lists of vanilla blocks, so modded blocks follow them too.
- `neoforge_version` in `gradle.properties` is also the minimum NeoForge version the mod declares, and must not be newer than the owner's modpack (21.1.248). Likewise `fabric_version` (Fabric API, 0.116.7) is the declared minimum in `fabric.mod.json`, and Fabric loader is pinned low (0.16.9). Don't bump these without a reason.
- A new `gradle.properties` key that resources need must be added to `expandProps` in `buildSrc/src/main/groovy/multiloader-common.gradle`.
- Everything the player can do must also be possible with a command, so every feature can be tested and debugged without its UI. Friendlier ways (recruiter, screen buttons, placement mode) never replace the command: foremen can always be summoned with `/journeymen foreman summon`, builders with `/journeymen builder summon <foreman>`, and builds started with `/journeymen foreman build …`.

## What the mod is

The player hires a **foreman** (a journeyman) and gives him a schematic; his crew of **builders** (journeymen too) build it **by hand**, like survival players. Nothing appears out of thin air, and it is not creative mode. The foreman only manages: he holds the job, the chests and the plan, and talks to the player. The builders carry, break and place. The name "Journeymen" leaves room for more trades (hauler, farmer, miner, …) as other journeyman types.

All commands live under `/journeymen`, with each trade as a subcommand (`/journeymen foreman …`, `/journeymen builder …`). `/journeymen help` lists them. There is no `/jm` alias, because JourneyMap owns `/jm`.

### Journeymen (foremen and builders alike)

- A custom `PathfinderMob` (not a villager) with its own AI goals, rendered with the vanilla player model: foremen with vanilla's Alex skin, builders with the default Steve skin.
- Has an owner (the player who summoned or hired it). Only the owner commands it. Operators (permission level 2+) can command any journeyman, addressing it as `<owner>.<name>` (e.g. `Steve.Gerald`), split at the last dot, so owner names that start with a dot (Floodgate's Bedrock players) work. An owner who logs in under a new name is known by it from then on. When that name matches several owners (a renamed player's old entries still carry the name until he logs in), the caller's own journeyman wins; anyone else is refused with the matches listed (the first 8 characters of each owner's UUID and the journeyman's position), never given the first one.
- Has a name: a random first name unique among all the owner's journeymen (foremen and builders share one namespace), or the one given at summon or hire. A name tag or `/journeymen foreman|builder rename <old> <new>` renames it. Commands address journeymen by name, and the name shows above its head. Names use only letters, digits, `_` and `-` (at most 24), so they never need quotes, and player names never contain the `.` separator.
- Owner, name and its role's data (below) persist through save/load. Right-click opens its screen.
- Can be hurt like a mob (falls, lava, mobs, other players under PvP rules), including by its owner, and regenerates slowly. `/journeymen foreman|builder kill <name>` removes it like a death.
- Can't be leashed, and isn't seated by touching a boat or a moving minecart; an op's `/ride` still seats it, until it has somewhere to go or is working. Journeymen don't push each other (players and mobs still push them), so a crew can share narrow ledges and pillars.
- When idle it stays where it is. `come <name>` walks it to you; `follow <name>` / `stay <name>` toggle following. All three are refused while it is working on a job.
- Walks through wooden doors and fence gates like a player: opens them on its way and closes them behind it if they were closed, leaving open ones open. Iron doors stay shut. Before opening one it asks the way its owner's right-click would (claims, spawn protection; the answer is kept for a minute, a refusal for 5 minutes), and a door or gate it may not use counts as a wall. It never closes one on anyone standing in the doorway, but closes it once the doorway is free (within 20 s), and closes the one it opened when it dies or unloads in the doorway. The doors and gates it still has to close are saved with it, so one whose chunk unloads before the doorway is free closes it once it is loaded again and the doorway is free, if it is still open (time spent unloaded doesn't count toward the 20 s).
- Never tramples farmland when it jumps or falls onto it (the game's `FarmBlock.fallOn` skips turning it to dirt for journeymen), so crops on it don't pop.
- Doesn't go through portals while it works on a job. Taken to another dimension anyway (`/tp`), a builder stops working there and waits (`waiting in another dimension`), and a foreman pauses his job, tells the owner and his crew waits; both carry on once they are back in the job's dimension.
- **Getting unstuck** (like a tamed wolf, but by time stuck): while it is going somewhere (for a builder: a chest it wants, the build site, the spot it picked to get within reach of the next blocks; for a foreman: his post at the site; for both: the spot it was called to with `come`, or its owner when following and at least 12 blocks behind) and for `stuck_teleport_seconds` (20, 0 = off) hasn't got 0.5 blocks closer nor broken, placed or fetched anything, it teleports to a safe spot next to that goal.
  - A safe spot has floor, room to stand, no fluid, fire or leaves, is in an entity-ticking chunk of the same dimension, in sight of the goal (within chest reach of a chest, within reach of the site's edge, 2–3 blocks from its owner), closer to the goal than it is, preferably outside the job area and never where the job will still place a block or clear the floor, and never inside another active job's area.
  - For the site it looks at the site's own levels (bottom to one above the top) as well as its own and prefers the site's, never the surface above it, so an underground, roofed or Nether site gets a spot beside it rather than on the roof.
  - A teleport takes it out of any boat or minecart first.
  - **Out of the way:** a journeyman that can't walk out of a spot within 3 s (a builder standing where its own block goes or where it clears a block over a deep drop, or any journeyman a builder asks to step aside) teleports to a safe spot within reach of that spot, line of sight not needed. With getting unstuck off, within the 30 s between teleports or with no such spot, the builder leaves that block for later and does others, and the foreman says once that it can't get out.
  - While its goal can't be reached it searches for a new path at most every 10 ticks once the last path ended where it stands, backing off to every 5 s.
  - Pauses (waiting for materials, a full dump chest, someone in the way) don't count as stuck time but don't reset it, so retrying an unreachable chest adds up. Working from where it is (see Reach) counts as progress.
  - It sounds and shows particles like a chorus fruit teleport and logs `Stuck for … teleported to …`. The owner is told only after 3 teleports within 10 minutes (then at most once per reminder interval), by the builder's foreman for a builder in a crew.
  - At least 30 s between teleports; with no safe spot it retries every 10 s, and the fallbacks (pausing for an unreachable chest or site) still apply. A journeyman told to `stay` never teleports by itself.
  - `/journeymen foreman|builder unstick <name>` does it at once: towards its current goal, the site (or a chest it is heading for) during a job, its owner when following, otherwise the player who ran the command.

### Foreman

- Hired at a Recruiter's Stall (see Survival UI) or summoned with `/journeymen foreman summon [name]` (ops).
- Has no inventory or armor slots, holds nothing and picks nothing up. On death he drops nothing.
- Holds the job, its plan and shared work list, the supply and dump chests, the pre-check stock, progress, the boss bar and every message to the owner (see Build jobs). He doesn't carry, break or place.
- **Crew:** the builders he hired or adopted, at most `max_crew_size` (8, 0 = no limit). Crews are fixed: a builder stays with its foreman until it or he dies. Membership is saved with the world, so he knows his builders while they are unloaded.
- **During a job** he walks to the site and stays at a post outside the job area within 8 blocks of its edge, stepping out if he ends up inside it or inside another active job's area (to a post outside every job's area) and walking back if he ends up farther.
  - The post he steps out to is the nearest spot he can walk to, 1–8 blocks outside any edge, preferably within 2 blocks of the site's levels, standable and not in water (so not over a cliff, in a moat or inside the ground of a dug-out pit). When he can't walk to any, the safe-spot search of getting unstuck picks one; when there is none he says so, stays where he is and searches again every 10 s.
  - When he can't find his way back to the site (getting unstuck off, or no safe spot), he stops trying for a minute after a minute without progress and says so.
- **Death:** a foreman that dies or is killed ends his job. The owner gets a notice naming the file, position, rotation and options, so giving the same build to another foreman continues from what is in the world (the plan is a diff). His builders finish the block in hand and become **orphans**: idle where they are, keeping their inventories. His chest assignments are lost.

### Builders

- Hired by a foreman (his screen's Crew tab, or `/journeymen foreman hire <foreman> [name]` within 8 blocks of him) and join his crew. Ops: `/journeymen builder summon <foreman> [name]`. Both are refused when his crew is full.
- Has a 27-slot inventory and armor slots. It wears its armor (rendered), which protects it and wears out like a player's. Inventory, armor, foreman and current task persist through save/load. On death or `kill` it drops its inventory and armor (also with `doMobLoot` off, and only once) and leaves its crew.
- Picks up items lying around itself (player pickup range), working or idle, but doesn't go out of its way for them.
- **Tools** in its inventory are items with a tool component (pickaxes, shovels, axes, hoes, shears, …) and damageable items the job's tool uses take (flint and steel). They are never dumped. Other damageable items it picked up or cleared out of a chest (armor, bows, fishing rods) are ordinary items: dumped like any drop the job doesn't need. The armor it wears in its armor slots isn't inventory and stays on.
- Takes no jobs and owns no chests. During its foreman's job it works the assignments he hands out (clear or place a batch, fetch from his supply chests, dump into his dump chests); otherwise it idles like any journeyman.
- **Foreman gone:** if its foreman unloads mid-job it finishes the block in hand and waits, and carries on when he loads. If he dies it becomes an orphan.
- A builder loaded but not yet ticked takes its foreman from the registry before anything (a rename, a name tag, its screen, `unstick`) writes its entry back, so an adoption made while it was unloaded stands.
- **Orphans** idle and obey `come`, `follow` and `stay`. Another foreman of the same owner adopts one with `/journeymen foreman adopt <foreman> <builder>` or from his Crew tab (refused when his crew is full).

### Schematics

- Formats: **Sponge `.schem`** (WorldEdit, v1, v2 and v3; v1 has no DataVersion and is read as 1.13.2 like WorldEdit does, block entities under `BlockEntities` or `TileEntities`), **Litematica `.litematic`**, **vanilla structure `.nbt`** and old **MCEdit / WorldEdit `.schematic`** (pre-1.13, numeric ids). Blocks and block entities from older Minecraft versions are upgraded with the game's own data fixers. Structure void, in every format, is no data: left alone, never placed.
- `.litematic`: all regions are combined over their overall bounding box. Positions no region covers have no data and are left alone, like structure void. Where regions overlap the later one (by name) wins with its own block entity or none, except where it has no data (structure void, an unknown block). Duplicate positions in a `.nbt` work the same way.
- `.schematic`: legacy id and metadata are flattened the way the game converted 1.12 worlds to 1.13 (`BlockStateData` and the chunk upgrade, which also takes bed and banner colors, flower pot plants, skulls, note block notes and door halves from block entities and neighbors), then upgraded. Block entities are upgraded too. Ids above 255 (old modded blocks) and ids the game never had are reported as unknown blocks and left alone. A `.schematic` that is really a Sponge file is read as one.
- Files are read server side from `schematics/` in the game directory, including subfolders (e.g. Create's uploads in `schematics/uploaded/<player>/`). A schematic is named by its path relative to `schematics/` with `/` (e.g. `uploaded/Steve/house.nbt`); paths that leave the folder are refused. Names with `/` or spaces need quotes, and the suggestions offer them quoted. The listing (suggestions, `schematic list`, the Job tab) skips folders it can't read and is kept for 2 s.
- Files are read with an NBT quota of 128 MiB, and every reader refuses an empty or negative size, or a volume over `max_job_volume` (and never over 2^26 blocks), before it allocates anything. Load errors name the file by its path relative to `schematics/`, never the server's own path.
- `/journeymen schematic list` lists them and `/journeymen schematic materials <file>` prints the material list.

### Build jobs

- `/journeymen foreman build <foreman> <file> [<x y z>] [rotation] [options]` gives him a job. `/journeymen foreman check` with the same arguments is a dry run that prints the pre-check. The arguments follow vanilla `/place template`: position defaults to where the player stands, rotation uses the vanilla names (`none`, `clockwise_90`, `180`, `counterclockwise_90`).
- **Origin:** by default the paste origin the file stores: the WorldEdit offset in a `.schem` or `.schematic` (`WEOffsetX/Y/Z`, like `//paste`), the litematic's own origin (region coordinates 0,0,0). `.nbt` files and `.schematic` files without an offset use the min corner. The `corner` option uses the min corner for any file.
- **Rotation:** 0, 90, 180 or 270 degrees clockwise around the origin; block states rotate with it.
- **Area:** the rotated bounding box. Schematic air is cleared; structure void and positions without data are left alone.
- **Options:** `corner`, `allow-breaking-enchanted`, `skip-unplaceable`, `skip-missing` (see Pre-check).
- **One job per foreman.** `build` is refused while he has one. `foreman cancel <foreman>` (also while he isn't loaded) stops it: his builders finish the block in hand and stop, the half-built structure stays, and leftovers stay in the builders' inventories and his chests. Issuing the same job again continues from what is in the world, because the plan is a diff.
- **Who works:** his builders that are loaded in an entity-ticking chunk, in the site's dimension and within the max site distance of it take part; the others wait (shown in `status`) and join in once they qualify. A builder frozen in a loaded chunk that doesn't tick drops out of the crew until it ticks again: its claims and reservations go, the others carry on, and what it carries is out of reach meanwhile. `build` is refused when none can take part, when the site is farther from the foreman than the max site distance, or when he has no way to walk to it (see Pre-check).
- **Getting there:** each builder fetches what the first stage needs from his supply chests (tools if there is anything to clear, otherwise materials for the first blocks plus any hoe or shovel for farmland and paths), then walks to the site. The foreman walks to his post; builders don't wait for him to arrive.
- **Chunks:** a journeyman stops when its chunks unload and continues when they load; builders wait while their foreman is unloaded. Work goes on while the owner is offline. A builder that has just loaded waits 5 s for its crewmates and the supply chests to load before it reports missing items.
- **Keeping chunks loaded** (`keep_chunks_loaded`, off by default): while a foreman has a job, the mod holds its own chunk tickets (not `/forceload`) on every chunk of the site and on the chunks of the foreman and of each builder on the job, all entity-ticking (a journeyman's ticket also covers the chunks around it, so it keeps ticking when it steps over a chunk edge), and keeps the level's entities ticking with no player online. Builders not on the job (waiting, too far) get none, and only the job's dimension gets tickets: a foreman or builder taken to another dimension gets none there. The tickets follow the journeymen, checked every second (by their last saved position while unloaded), and are dropped within a second when the job finishes, is cancelled or the foreman dies, and when the option is turned off and `/journeymen config reload` runs. They aren't saved: after a restart the jobs in the world's registry get them back within a second, which loads the foreman and his builders where they were saved.
- Limits: a config cap on job volume (default 256×256×256); two active jobs' areas may not overlap.
- **Saving:** the job is saved in the world's journeyman registry under the foreman, so the overlap check sees it while he is unloaded. Its tampering redo counts, the positions it gave up on and the blocks it skipped are saved with it, so they stay so after a restart, and so are the schematic's size, paste offset and a hash of the file. When the foreman loads the job again after a restart and the file has a different size or paste offset (the paste offset only without `corner`), he stops the job, tells the owner the file changed and frees its area; when only its contents changed he carries on with the new contents (the plan is a diff) and tells the owner once. Each builder keeps only its foreman's id and its own task; claims and reservations are rebuilt from a fresh plan when the foreman loads. A builder whose job was cancelled or finished while it was unloaded drops its task when it loads, and one whose foreman died meanwhile loads as an orphan.

### Shared work list (how a crew splits the job)

- **One plan:** the order rules stay: the area is cleared before anything is placed, and placing goes bottom-up with hanging blocks after their supports and the access staircase filled last. Within that, each builder claims a batch of nearby work sized to what it can carry, preferring blocks it already carries items for, so no two builders take the same block.
- **Batches:** a batch comes from one layer (one group: supports, access staircase, hanging blocks, fluids) and takes the next blocks in each column only (bottom-up for placing, top-down for clearing), so a builder may start the layer above in columns whose lower blocks are done while others finish theirs. Its size is the builder's share of the layer (layer size divided by the working builders, at least 8 blocks for placing, 4 to 64 for clearing), cut down to what fits in its free slots and what it carries or can fetch. A builder working alone (or whose crewmates aren't loaded) takes the next blocks one by one, with no batches.
- **Shared stock:** the foreman's supply chests and his builders' inventories count as one stock in the pre-check. The items for a claimed batch are reserved, so nobody else fetches them; claims and reservations are released when a builder finishes its batch, dies or is unloaded.
- **Fetching:** with a batch a builder fetches its reserved items plus its share of the materials for the next unclaimed blocks, as much as fits. When its batch no longer fits (it picked up a tool since claiming) and it has nothing to unload, it carries what fits and fetches the rest on a later trip. Reservations count only fetchable stock (supply chests minus other builders' reservations) plus the builder's own inventory, and a fetch uses up its reservation. Items in a builder's inventory are used by that builder, who claims blocks it carries items for first. A builder that has nothing it can claim because the items it needs sit in a crewmate's inventory waits instead of pausing, and once it has waited 5 s it hands the job materials it carries back to a supply chest (with none to hand back, it looks again every 5 s while it waits). When the supply chests have no room for them (or there is none) while a builder of the crew waits like that, the builder pauses and the foreman says `My builders are waiting for materials other builders carry, and my supply chests have no room to take back what they need to hand over. Please make room in my supply chests.`, repeated at the reminder interval while it lasts; they try again every few seconds. A builder starting a new batch while a crewmate waits like that does the same with what its batch doesn't need. When the crew's stock (supply chests and the crew's inventories) runs short of an item the rest of the job needs, the shortfall is fetchable from the dump chests too (see Supply and dump chests), with the same claims and reservations. Only when the whole crew lacks an item, the dump chests don't have it either and no block still to clear would drop it (see How a build plays out → Missing items mid-build) does the missing-items pause (or `skip-missing`) happen.
- **Tools:** each builder fetches its own tools from the supply chests, as many as its share of the remaining blocks (remaining blocks divided by the working builders) calls for (see Breaking → How many tools), but at most its fair share of each kind: (that kind in the supply chests and in the crew's inventories) divided by the working builders, rounded up, so four shovels for two builders means two each. The pre-check pools durability across all of them. A builder only claims blocks that need a tool when it has a suitable one (one diamond pickaxe means only one builder mines obsidian); blocks a tool only speeds up are claimed either way and dug by hand when it has no tool left for them. One waiting for a tool that only a crewmate holds gives up its batch and waits.
- **Getting along:** a builder blocked from placing by a journeyman standing in the spot (a crewmate, another crew's builder or foreman, an idle one) asks it to step aside and, in a crew, does other blocks of its batch meanwhile (no "someone is standing" message unless it doesn't move); one that has waited 3 s with nothing to do walks off the site.

### Pre-check (core requirement)

`build` and `check` run the same check. A job starts only when everything passes; otherwise it lists every problem at once. The check changes nothing in the world.

- **Crew:** at least one of the foreman's builders can take part (see Build jobs).
- **Path:** the foreman must be able to walk from where he stands to within 8 blocks (horizontally) of the site, inside it counting too. The check searches with the journeymen's own walking rules (doors and gates open, partial blocks, drops up to his safe fall distance), at most 16,000 steps and no farther than 32 blocks around him and the site. It fails only when it has searched everywhere he can walk without coming within 8 blocks (he is boxed in, or on a ledge or platform he can't get down from). When the search runs out of steps, reaches its edge or an unloaded chunk first, the check passes with a warning and he tries to walk there (getting unstuck if he can't). Builders' paths aren't checked: they walk to the supply chests first, work from where they are when they can't get within reach, and get unstuck like him.
- **Materials:** every item needed for placing must already be in the foreman's supply chests or his builders' inventories (only builders that can take part); drops from clearing don't count.
- **Chests:** a supply or dump chest (or the other half of a double one) inside the site fails the check, naming the chest, since the crew would clear it. Only plain items count and are used: no custom name, enchantments, contents or other vanilla data (a renamed chest or filled shulker box is never placed). Data other mods add is ignored when matching, so TFC metal items (`tfc:heat`) and TFC food blocks (creation date) count.
- **Tools:** every block to clear that needs a tool tier needs such a tool, with enough durability for all the blocks it will break, counted conservatively (1 per block, Unbreaking ignored). 10 obsidian and a diamond pickaxe with 9 durability left fails.
- **Enchanted tools** are never used below 1 durability, so the check counts them as having 1 less; `allow-breaking-enchanted` lifts this. Plain tools can be used up. An enchanted tool worn down to that last point counts as no tool at all: a builder carrying one fetches another of the same kind and puts the worn one back into the supply chest it fetches from (or the one of its next tool restock).
- **Made blocks:** a block that drops another block which a hoe or shovel turns into it is made like a player would: farmland = dirt + hoe, dirt path = dirt + shovel, and the same for modded soils (TFC farmland and grass paths). The tool use counts toward durability; any tool that can till or flatten works. Where the game says the made block can't stay given the schematic's own neighbours (its `canSurvive` against the schematic's blocks, the world where the schematic has no data: a path or farmland under a solid block turns back into dirt), it is planned as the block it is made from, with no tool use, and counts as done once that block (or the made block) is there; the material list, pre-check, `supply` and `missing-only` follow.
- **Water:** a block that holds water (waterlogged, kelp, seagrass) needs a full bucket of it, except where the world already has a water source in that spot. A dry waterloggable block going into a water source, and a waterlogged block in the world that the schematic wants dry, need an empty bucket each: any empty container that can take a bucket of water through the loader fluid APIs counts. The check names it when there is none.
- **Grass:** blocks with a `snowy` state (grass block, mycelium, podzol, TFC grass) are placed as the block they drop without Silk Touch (dirt, TFC dirt) and count as done once that is there; the grass spreads by itself. The other way round, a plain dirt target that grass, mycelium or podzol spread onto counts as done too. Blocks that drop no block (TFC clay grass drops clay) still need their item.
- **Finished by using items:** a block a player makes by placing a plain block and then using items on it costs those items too, and is made that way (see Placing): a filled cauldron is a cauldron plus the bucket that fills it (water, lava or powder snow; a water cauldron below full also takes a glass bottle per level, used to take that level out again, which gives a water bottle back; a powder snow cauldron below full can't be made by hand), a charged respawn anchor glowstone per charge, an end portal frame with an eye an eye of ender, and lit candles a flint and steel use (any damageable firestarter; counted toward durability like hoe uses and supplied by `supply`; fire charges aren't used). Emptied buckets come back. Campfires need nothing extra: the game places them lit. Glow lichen, sculk veins and vines cost one item per face. Powder snow costs its bucket, and the empty bucket comes back. The rules come from the block classes (cauldrons whose item places another cauldron block, `RespawnAnchorBlock`, `EndPortalFrameBlock`, `AbstractCandleBlock`, `MultifaceBlock`, `VineBlock`, `SolidBucketItem`); which bucket fills which cauldron is a short list (water, lava, powder snow), as the game has no lookup for it.
- **Can't be placed by hand:** blocks with no item (TFC's forge, fire, portals) fail the check. Blocks whose item survival can't get (TFC clay grass, bedrock) show up as missing materials.
- **Skipping:** `skip-unplaceable` leaves blocks that can't be placed by hand alone, like structure void. `skip-missing` lets the job start with materials missing; a block whose items the stock lacks is then skipped instead of pausing. The check names the option when its problem is present. Skipped blocks are reported when the job ends and not retried by the tampering pass. Tools are always required.
- **Unbreakable blocks** (destroy speed < 0: bedrock, barrier, end portal frame, reinforced deepslate, …) in the clearing area fail the check.
- **Water left behind** (warnings): water or lava sources where the schematic wants air; ice to clear where the schematic wants air that melts into water (the game's `IceBlock` rule: something solid or liquid below, not in the Nether) when no Silk Touch tool is in stock; blocks to clear there that hold water or lava (waterlogged blocks, kelp, seagrass).
- **Falling blocks above the site** (warning): gravity blocks stacked right above the site's top layer where it will be cleared or stays free, with how many and where. What falls in is cleared again like any tampering.
- **Protection:** builders break and place through a fake player with the owner's identity, so claim and protection mods allow it exactly where the owner could build. The check asks spawn protection and the world border directly, and claim mods the way a player starts mining (NeoForge's left-click block event, Fabric's attack block callback, empty hand). It never fires block break or place events, because other mods act on them (TFC cave-ins and landslides). Positions the owner may not start mining fail; a position protected only against placing passes, is skipped at build time and reported at the end. Placing asks NeoForge's entity place event, and on Fabric (whose API has no place event) the use block callback, which claim mods also use to stop placing; neither fires a break event.
- Size and distance limits.

### Supply and dump chests

- They belong to the foreman: `/journeymen foreman chest <foreman> add <x y z> supply|dump`, plus `remove` and `list`. Several chests per role are used in order, up to `max_chests` (128) in all; TFC's stack caps make big builds need many (TFC_Home_P5_Industry fills 27 single chests, or roughly 80 large vessels). Both halves of a double chest count as one, whichever half was assigned: `remove` takes either half, two assigned single chests that later join count once, and when the assigned half is broken the other half is used. Any block with an item inventory works, including modded storage that only offers the loader's item API (TFC barrels and large vessels, drawers). In survival they are assigned with link mode (see Foreman screen).
- **Dimension:** a chest belongs to the dimension it was assigned in (`chest add` runs in the foreman's dimension, link mode in the player's; saves from before this was stored take the foreman's dimension). Only the job's dimension counts: chests elsewhere are left out of the stock, the builders' visits and the double-chest refresh, and the pre-check warns about each (`The supply chest at … is in minecraft:overworld, not in minecraft:the_nether where the site is, …`); it fails only through the usual missing-items problem when the other chests don't cover the job. Link mode toggles only chests in the player's dimension, `chest remove` takes the chest at those coordinates in the dimension it runs in, and `chest list` and the Chests tab name the dimension of a chest that isn't in the foreman's.
- **Only chests the owner can open:** `chest add` and link mode refuse a container that is locked (vanilla `Lock`) or that the owner may not open: spawn protection and the world border, and claim mods asked like a right-click with an empty hand (NeoForge's right-click block event, Fabric's use block callback) through the owner's fake player, without opening anything itself (a click another mod handles and cancels with a success, as TFC does for its large vessels, counts as allowed; one cancelled otherwise, or with the block use denied, counts as refused). Both halves of a double chest count. An op adding a chest to another player's foreman gets the owner's answer, not his own. A chest locked later counts as gone: the pre-check and the stock leave it out (the pre-check warns that it is locked, but doesn't fail for it, so the other supply chests can still cover the job), and a builder re-checks the lock at every visit. A locked supply chest pauses the job with `The supply chest at … is locked …` (missing-items pauses add `My supply chest at … is locked.`) until it is unlocked or the items are found elsewhere; a locked dump chest is reported like a full or gone one. Builders ask the owner's rights again at their visits, cached like door rights (an allowed answer for a minute, a refusal for 5 minutes), and the pre-check and `supply` ask afresh; a chest the owner may no longer open (a claim made later) counts as locked, with `<owner> isn't allowed to open the supply chest at … (spawn protection or a claim)` in the pre-check's warnings and the pauses.
- **Supply chests** are stock: his builders take the materials and tools they need from them, and they count in the pre-check. Builders never dump into a supply chest; only drops the stock is short of go into one (see Breaking). Materials a builder hands back or puts back to make room are job materials only, at most what the job still needs; anything else goes to a dump chest. Whatever a builder puts back (drops, materials, extra tools) goes into the first supply chest with room, not only the first one.
- **Getting to a chest:** a builder walks to within 4 blocks of the chest (eye to chest center), however far it is: it gives up only when it hasn't got 0.5 blocks closer for `stuck_teleport_seconds` + 10 s (30 s; 20 s with getting unstuck off), so getting unstuck gets its chance first. Like every journeyman walk over 40 blocks, it goes in path segments of up to 64 blocks towards the goal, taking a random step towards it only when no segment gets 8 blocks closer. A fetch trip skips chests that no longer hold anything it wants. Until it takes or puts anything, a builder checks every tick that the foreman still has it in the role the visit is for, and drops the visit when the chest was removed or changed role (`chest remove`, then `chest add` with the other role) on its way; it then fetches from or dumps into the chests he has now.
- **A chest nobody can get to:** when a builder gives up on a chest, the whole crew leaves it out for 5 minutes (fetching, unloading, dumping, and the stock it reserves and claims blocks for), it carries on with the other chests of the trip, and the foreman says once (repeats collapse until the reminder interval): `My builders can't get to the supply chest at <pos>. Clear a way to it (they need to get within 4 blocks of it) or move it; until then they use my other supply chests.` If the items are only in such a chest, the missing-items pause names it.
- **Dump chests** take builders' drops when their inventories are full, and whatever they don't need once the site is clear. With no dump chest, or none a builder can use, the crew pauses and the foreman asks, naming each dump chest that is full, gone, not loaded or out of reach. Messages about a full inventory also name supply chests that are gone or not loaded.
- **Dump chests as a last resort:** when the stock (supply chests and the crew's inventories) holds less of a material than the rest of the job needs (counted from the world, so a block lost mid-job counts), builders take the shortfall from the dump chests, like a player taking back the dirt he dumped: only the shortfall, never instead of supply, and from loaded dump chests they can get to. What they take is a job material, so it is kept and placed, not dumped again. This is a build-time fallback only: the pre-check still counts only supply chests and builders' inventories (`… are in a dump chest, which doesn't count as stock`). Tools are never taken from a dump chest.
- `/journeymen foreman supply <foreman> [<file> [pos] [rotation] [options]]` (ops only, creates items) puts a job's full material list into his supply chests, plus the cheapest plain tools that cover the job's tool uses (enough wooden pickaxes for the stone, a diamond pickaxe for obsidian, a hoe for farmland). Without a file it uses the current job. What doesn't fit goes to the player's inventory. All or nothing: if anything doesn't fit it gives nothing and says how much didn't fit.
- `missing-only` (in the options, or right after the foreman name for his current job: `supply <foreman> missing-only`) gives only what the pre-check finds missing: materials the stock lacks, and tools for uncovered tool uses (one plain tool kind at a time, the one that can mine the most of the uncovered blocks first, so a diamond pickaxe for obsidian also covers the stone). Same placement and all-or-nothing rules; when nothing is missing it says so.

### How a build plays out (core requirement)

"It" below is the builder doing the work; every message to the owner comes from the foreman, once for the crew.

1. **Plan:** the foreman diffs the schematic against the world into blocks to remove and blocks to place.
2. **Clear** the whole area first, top-down. Then place.
3. **Reach:** it walks until the block is within horizontal reach (4.5 blocks). Height doesn't matter: it reaches any height, so there is no scaffolding or pillaring. Of the blocks next in order (preferring those it carries the items for, so what it fetched gets placed before it goes back for more) it takes one within reach, otherwise the nearest one it can walk to within reach (a path search over the site among the 256 nearest of them), so it never waits on an unreachable block while others are reachable. Only when it can't get within reach of any (lava pool, void) does it work from where it is. The path search follows its walking rules: a partial block sticking up above its floor (TFC mold table or channel, carpet, flower pot) raises the floor if low enough to step onto, so climbing onto a block with one on top is too high a jump; taller ones are jumped onto like full blocks; it never plans to stand where its head would hit something; a block whose sides rise more than a step above its own floor all round (an open TFC barrel, which a builder fits inside but can't walk into) counts as a wall, while one walled on some sides only (a ladder) is still walked through. If it stops getting closer to the spot it picked, it gets unstuck; with that off or no safe spot, it works from where it is and doesn't search again from the same place for a while (5 s, doubling up to 30 s).
4. **Breaking:** look at the block, swing, show crack progress (`destroyBlockProgress`), with player break time for the held tool. It breaks through the owner's fake player with vanilla survival breaking, so tool wear, two-block blocks (doors, beds) and container contents behave as for a player.
   - **Ice** that would melt into water (the game's `IceBlock` rule) is broken with a tool whose enchantment keeps ice from melting (Silk Touch, the `prevents_ice_melting` tag) when the crew has one: a builder without one fetches it from supply first, or leaves the ice to the crewmate holding it.
   - It never breaks a block a journeyman stands on when the fall through it would be longer than that journeyman's safe fall (6 blocks when healthy): it picks a spot to stand that isn't such a block, asks anyone else on it to step off, and does other blocks meanwhile.
   - Tools: the fastest tool it has for each block. For blocks that need a tool it uses the least versatile one that works (an iron pickaxe for stone when the diamond one is needed for obsidian), and uses a tool on other blocks only when that durability isn't reserved. Reserved are the uses the remaining blocks that need a tool take, and the hoe, shovel and other tool uses the rest of the job's placing takes (farmland, paths): a builder holding the one wooden shovel `supply` gives for 50 paths uses it on dirt only as long as 50 uses stay on it, then digs the rest by hand. The tool uses are reserved once for the whole crew, not once per builder: a builder keeps on its own tools only what the supply chests' tools and its loaded crewmates' tools can't cover (crewmates' inventories counted at each break, the supply chests re-read after any chest visit of the crew and every 5 s), so the crew as a whole always keeps the uses the placing needs (a crew of three with three wooden shovels for 50 paths digs dirt with the other 127 uses). The tool count below counts only the unreserved durability, and a kind with none left over isn't fetched for clearing.
   - **How many tools:** it restocks tools from supply before walking to the site, after every trip to a dump chest and whenever it runs out (below). Tools that help on the same remaining blocks form one kind (any shovel for dirt, sand and gravel), and each remaining block counts for the kind it would use (the least versatile kind for blocks that need a tool, otherwise the fastest). A tool provides its remaining uses for its kind's blocks; a free slot holds one stack of drops at the drop's real stack size (64 dirt, 32 TFC dirt), counted from what the remaining blocks drop with that tool. Worn-out tools free their slots, so with `C` slots not taken by other items it keeps across trips (drops don't count: they leave on the next dump trip) it carries `ceil(C / S × U / D)` of each kind, where `S` is drop slots per remaining block, `U` the kind's tool uses per remaining block and `D` the average durability left on that kind's tools: the tools wear out about when its inventory is full of drops, and the dump trip restocks both (2048 vanilla dirt with stone shovels: 13 shovels, about 1700 blocks per trip). It carries at least one of each kind with remaining blocks, never more than the kind's remaining work needs (`ceil(uses left / D)`), and at most `C / 2` tools in all. Tools beyond that, and tools no remaining block needs, go back into a supply chest on the next restock; tools are never dumped.
   - **Running out:** with no tool left for a block that needs one, it fetches one at once. When a tool that only speeds a block up (a shovel on dirt, an axe on logs) runs out and supply holds a faster one, it fetches more (by the calculation above) only when the time that tool saves on its share of the remaining blocks it speeds up (break ticks by hand minus with the tool) is more than twice a round trip to that chest (at 4 blocks per second); otherwise, near the end, it digs by hand and asks again after a minute. When its inventory is over half full it empties into a dump chest on the way. With no free slot at all it always empties first (while placing, everything beyond the next blocks' materials: junk to a dump chest, job materials to a supply chest), then fetches the tool; when nothing can go, the crew pauses with the full-inventory message instead of walking back and forth.
   - Drops go straight into its inventory, never on the ground, including drops that come a tick later or farther away (sugar cane, bamboo or cactus above popping one block per tick, blocks hanging below, falling dripstone): for 3 seconds after a break it also takes item entities that appeared since then in the broken column (1.5 blocks around it, 24 up and down), but never items a player threw (they have a thrower) or that were lying there before the break. What doesn't fit is held (and saved) until it reaches a dump chest. When the job ends (finished, cancelled, its foreman gone) it keeps holding them, moving them into its inventory as room frees up, and its next job's dump trips take them. When full it walks to a dump chest and leaves everything but its tools there, including drops the job places later: the pre-check already put every material in the stock, so the inventory stays free for tools and digging. Only drops of an item the stock is short of for the rest of the job (with `skip-missing`, or something was taken out, or a block already built was broken or moved since, by a landslide, a player or the tampering pass; the rest of the job is counted from the world as it is now, not from the plan the pass started with; the stock is the supply chests plus, in a crew, the other builders' inventories) go into a supply chest instead (the first with room, then the next), so they get used. Items it picked up are treated the same. It never holds drops for later. If nothing can be dumped, it returns tools it carries beyond what it needs to a supply chest with room, then stores those drops. When that isn't possible either (supply chests full, or nothing but tools it needs), the crew pauses and the foreman says what fills its inventory instead of blaming the dump chests.
   - When the site is clear it takes everything else it collected to the dump chests even if not full, and the drops the stock is short of to the supply chests; if the dump chests are full, gone, not loaded or out of reach the foreman says so and it keeps the rest; without a dump chest it keeps everything.
5. **Fluids in the way:** water or lava where the schematic wants a block is no obstacle: the block goes straight into it, as a player places into water (see Placing). Where the schematic wants air (or flowing water), only a **source** pauses the crew: at the first one (in the same top-down order) the foreman tells the owner the position and they check again every few seconds; each reminder interval it stays counts as one redo of that position, and past the redo limit they leave it and it is reported at the end. Breaking ice without Silk Touch, kelp, seagrass or a waterlogged block leaves such a source. **Flowing** water or lava there doesn't pause: once everything else is done the foreman waits 3 s for it to drain and reports the positions where it is still there.
6. **Placing:** bottom-up. It places anywhere within reach (no supporting neighbor or line of sight needed), straight into replaceable blocks (short grass, snow layers) and into water or lava, source or flowing, like a player. A waterloggable block that goes into a water source is waterlogged by it, as the game does; if the schematic wants it dry, the builder first scoops the water with an empty bucket (the filled bucket comes back to its inventory). Each block consumes its item with a swing and a sound. The block state (facing, half, axis, …) is kept and rotated. Special cases follow the material list (redstone wire → redstone, double slab → 2 slabs, potted plant → pot + plant, …); doors and beds place both halves from one item.
   - **Finishing with items:** a block finished by using items (see Pre-check) is placed as the plain block (empty cauldron, uncharged anchor, empty frame, unlit candles), then each item is used on it through the game's own interaction (the cauldron interactions, `RespawnAnchorBlock`, `EnderEyeItem`, which also opens an end portal when the ring is complete), or lit with the flint and steel. A container the use empties or fills (bucket, water bottle) comes back to its inventory. When the plain block is already there it is finished in place, not broken and replaced. If a use doesn't take, the leftover items come back and the spot is reported.
   - **Rails** keep the schematic's shapes: the game reshapes a rail, and rails next to it, when one is placed (parallel tracks and junctions bend). After each placement the builder sets the new rail back to its planned shape and puts any rail next to it that changed back the way it was, which is the state a player gets by placing them in the right order. It doesn't loop: a shape set this way only changes again when another block is placed next to it.
   - **Bare farmland** (no crop planned on it) that only the schematic's water keeps moist is tilled only once that water is close enough (the game's own `FarmBlock.isNearWater`), like the blocks that need water, so it can't dry back to dirt before the water arrives and needs no second hoe use.
   - **Hanging blocks** come after all other blocks, each once its support can hold it. The game's survival rule decides which: a block that couldn't stay with only air around it (torches, doors, rails, redstone, carpets, plants, vines, lanterns, modded shelves, …), plus gravity blocks (`FallingBlock`) whose block below, in the finished schematic and the world around it, is free by the game's `FallingBlock.isFree` rule or is itself one of them. One whose support never comes (sand over schematic air, structure void or open air below the site) is skipped and reported, never placed to break or fall.
   - **Blocks that need water** go with the hanging blocks: those that survive among the schematic's blocks only with its water (sugar cane by a water channel, lily pads, small dripleaf on dirt), and living coral (`CoralBlock`, coral plants and fans), which dies without water. One the schematic has holding water (waterlogged, or kelp and seagrass) is placed with its water in the same action, emptying a bucket into the spot (or straight into a water source already there), so it never stands dry; the others wait until the water they need is in the world. When no hanging block can go in yet, the fluids are placed first (below) and the rest follow.
   - **TNT** goes after every other hanging block, and only when it would get no redstone signal at that moment; otherwise it is skipped and reported, never primed.
   - **Restocking:** it fetches the next blocks' materials (and, when it has none, one hoe or shovel of each kind for farmland and paths, fetching another when it wears out) from supply before walking to the next block, as much as fits. The next blocks are the block it is about to place, then the rest in building order, as many as its slots hold. When the next blocks need more room than it has free, it unloads in one trip (junk to a dump chest, job materials beyond the next blocks back into the first supply chest with room), then fills up. On a trip through several supply chests it leaves room for the next blocks' items that come from a later chest. If no supply chest has room it stops trying that for a minute and carries what fits; it pauses only when it can't make room for the block it is about to place.
   - **Getting around:** builders may walk on the structure as it rises and drop up to 6 blocks (taking fall damage) when healthy. Along the site edge nearest the foreman's first supply chest the plan keeps a one-block-wide staircase notch of the schematic's own blocks (each step one higher, blocks above the steps left out), so builders can walk back onto a raised structure. It is filled after all other non-hanging blocks, top step down, before the hanging blocks.
7. **Flowing fluids in the schematic** (non-source water or lava) are treated like air: a solid block there is cleared, and any fluid there counts as done.
8. **Growth stages:** crops, saplings and other aging blocks are placed young (age 0) and grow on their own. Right after tilling farmland it plants the crop on top, so the farmland doesn't dry out. Leaves are placed persistent. What grew from a planned block by the game's own growth counts as done and is left alone: a sapling whose spot holds a log (the tree's trunk), with the tree's logs and leaves in the schematic's air connected to it; a randomly ticking plant (sugar cane, cactus, bamboo, kelp, cave, twisting and weeping vines, vines) whose spot or column above and below, in air or water the schematic wants, holds a block placed with the same item (bamboo from a bamboo shoot, kelp plant from kelp); vines with more faces than planned. Growth that takes the place of a planned block is still cleared. The rule comes from the game (`isRandomlyTicking`, the item a block is placed with); the sapling rule uses the `logs` and `leaves` tags. States that come from neighbors (fence, pane and wall connections, stair shape, redstone wire connections and power, `lit` except on candles, `powered`) are not compared; a block counts as done in the state the game itself gives it at that spot from its neighbors and contents (e.g. a TFC shelf's item flags).
9. **Block updates** happen as for a player, so a half-built contraption may fire.
10. **Fluids last:** water and lava sources and waterlogging go in after every solid block (or as soon as the remaining hanging blocks wait for water), with any item holding a full bucket of that fluid (vanilla, TFC wooden and metal, other mods' buckets). The emptied container comes back to its inventory. Before pouring it checks the spot and the cells the fluid would flow into right away (below and the four sides, where the game lets it flow): a mob or player there makes it do the other fluid spots first and then wait (the foreman reports it after about 10 seconds like someone in the way), a crewmate is asked to step aside, and it steps out itself. While fluids remain, its reach search prefers standing spots that are none of those cells.
11. **Block entity data:** it copies sign text (with dye color and glow when it has the dye or glow ink sac) on signs and hanging signs, keeping plain text, colors and styles but never click or hover events, insertions, or score, selector and nbt components (vanilla runs sign click commands at permission 2, and anyone can upload a schematic through Create); written books in the material list (lectern, chiseled bookshelf, decorated pot) are stripped the same way, banner patterns (needs the patterned banner), and decor contents from stock (flower pot plants, lectern books, decorated pot item, chiseled bookshelf books, jukebox disc). Container contents are not copied. Entities (item frames, paintings, armor stands, mobs) are ignored.
12. **Wrong state:** if the right block is there in the wrong state and a right-click fixes it (door, trapdoor or gate open/closed, lever, repeater delay, note block pitch, comparator mode), it right-clicks with vanilla's interaction until the state matches. A block waterlogged where the schematic wants it dry is drained with an empty bucket (the game's bucket pickup, in the fluids phase); a dry one the schematic wants waterlogged gets a water bucket. Otherwise it breaks and replaces the block.
13. **In the way:** if a player or mob stands where a block goes, it waits; the foreman tells the owner after about 10 seconds, naming who (`A pig is standing at …`, `Steve is standing at …`), then reminds every few minutes. Something that doesn't move by itself (an armor stand, a minecart or boat with nobody in it) is named the same way with `… is in the way at …, where … needs to place a block. It doesn't move by itself, so please move it.` Builders never break or move other players' entities. It never places a block inside itself: it steps out first (see Getting unstuck → Out of the way). Blocks that have no collision box but act on whoever is inside them (powder snow, cobwebs, sweet berry bushes, fire and modded ones alike: the block reacts to entities inside it) count as full blocks here, so they are never placed into anyone.
14. **Missing items mid-build** (taken out, or the world changed): first the builders take what the stock lacks from the dump chests (see Supply and dump chests). When they don't have it either, the builder re-checks the area: blocks became "to clear" during the placing pass (a landslide or falling block that left the spot it was placed on, blocks someone put on the site) are otherwise only cleared after the pass, which a pass waiting for their items never reaches. If any of them is within the redo limit and would drop a missing item (the game's loot tables, by hand or with a tool the crew has: in a builder's inventory or a supply chest), the pass ends there like a tampering re-check: those positions and the blocks placed in this pass that were undone since count one redo each, the crew clears every block to clear first (what they drop that the stock lacks is kept or stored in a supply chest, not dumped), then places again. The re-check runs at most every 5 s for a crew. Only when no such block is left: pause, the foreman tells the owner exactly what is missing (and that his dump chests don't have it), and work continues once it shows up in the stock. With `skip-missing` the block is skipped instead, also only after that check.
15. **Tampering:** before finishing the foreman re-checks the area and his builders fix differences, each position at most N times (config, default 3), so griefing one spot can't loop it. Positions over the limit are reported. Each re-check waits for falling blocks over the site to land first, so gravity blocks falling in from above are cleared again (and counted) rather than missed. Then he tells the owner it finished, the job ends and everyone stays where they are.
16. **Speed:** player pace, with a config multiplier.

### Feedback

- `/journeymen foreman status <foreman>`: the job (file, phase: walking, clearing, building, paused; percent done; what it is waiting for) and a `Crew of N` list with what each builder is doing (or `not loaded`, `not ticking`, `in another dimension`, `too far`). `/journeymen builder status <builder>`: its foreman (or orphan) and its current task. Both show how long it has been stuck, and when, from where and to where it last got unstuck (saved with the world).
- One boss bar per job shows progress to the owner within 64 blocks of the foreman, e.g. `Ann's crew · house2.nbt · placing 45/92`: green while working, yellow while paused. The placing total is the pre-check's "to place" plus "to adjust", and both count what builders do: a door or bed is one placement (its other half isn't counted), and waterlogging a newly placed block is one adjustment. Blocks skipped or found already done come off the total, so progress ends at its total. The bars are also checked from the server tick every half second, so a bar goes when its foreman stops ticking (unloaded, or in a loaded chunk that doesn't tick), is gone or has no job, or its owner is out of range, even though the foreman's own tick no longer runs.
- Messages (pauses, missing items, chests gone, finished, a foreman's death) go to the owner in chat at any distance and to the server log. If the owner is offline they are saved with the world and delivered on login (repeats collapsed, at most 20 kept); `/journeymen notices` shows them too. While paused the foreman reminds every few minutes.

### Config

A small config file (`config/journeymen.toml`, hand-written with a comment, range and default above each key) read by `common/`, same format on both loaders, no library dependency. `/journeymen config reload` (ops) rereads it and tells the op who ran it every problem. Keys include the speed multiplier, `keep_chunks_loaded` (false), the redo limit (3), the max job volume, the max walking distance to a site, the reminder interval, `stuck_teleport_seconds` (20, 0 = off), `max_crew_size` (8, 0 = no limit), `max_chests` (128 per foreman, 1 to 1024) and the hire price keys (see Recruiter's Stall).

- Format: `key = value` lines and `#` comments, TOML-style: strings may be quoted (`hire_cost_item = "#c:gems/emerald"`, written that way), and a `#` after a space starts a trailing comment (an unquoted value may still start with `#`, like a tag).
- Problems (a line that isn't `key = value`, a value out of range or unreadable, a key set twice, an unknown or misspelt key, a read error) are logged as warnings and reported by `config reload`. Values that loaded fine apply, invalid ones use their defaults, unknown keys are kept, and a file with any problem is never rewritten. The file is written (through a temporary file and an atomic move) only when it is missing or lacks keys; the config screen's Save writes it whole and keeps unknown keys at the end.
- Ranges keep tick counts from overflowing: `reminder_interval_seconds` 1 to 86400, `wait_report_seconds` and `stuck_teleport_seconds` 0 to 86400, `speed_multiplier` 0.01 to 100.

**Config screen** (common `ConfigScreen`, vanilla widgets): opened from the Mods list's Config button, NeoForge's through `IConfigScreenFactory` and Fabric's through Mod Menu's `modmenu` entrypoint. Mod Menu is optional: compile-only from the TerraformersMC maven (`modmenu_version`), and `-Pwith_modmenu=true` adds it to Fabric's dev runs. The screen lists every key with its comment, its range and default: a toggle for booleans, a text field for numbers and `hire_cost_item`, checked with the same parsers and range checks as loading (invalid values in red, listed above the buttons, and Save stays off until all are valid; an item id that doesn't exist only warns). Each key has a Default button; Save writes the whole file the way loading does and applies it like `config reload`, Cancel discards. It edits only the local file: from the main menu, and in single player, where it applies to the running world at once (the integrated server shares the values; chunk tickets update on its thread). Connected to another server it is read-only with a note that the server uses its own `config/journeymen.toml`; server values are never fetched or sent.

## Survival UI

Everything below also stays possible with a command (see Architecture rules).

### Recruiter's Stall

- A craftable item (shaped data recipe so modpacks can replace it: wool across the top, planks + emerald + planks, sticks at the bottom corners; the emerald is the `c:gems/emerald` tag so TFC's cut emerald works). Placed like a bed: one right-click builds a 3 wide, 2 deep, 3 tall stall facing the player, if the space is free (with the spot in front of the counter) and the player may place every part (the same place probe as the builders' placing). Vanilla textures only: plank counter, spruce posts, striped wool awning.
- Breaking any part removes the whole stall and drops one stall item, explosions too: the core always drops it (its loot table has no explosion chance), whichever part an explosion hits first, and the other parts drop nothing.
- It isn't built into a player or mob: a part with collision that would overlap one refuses the placement (item and command alike).
- Placing it spawns a **Recruiter** (villager look) behind the counter, who disappears with the stall. Building a stall first removes any recruiter left from an earlier stall at that spot, so breaking and replacing it quickly never leaves two. The recruiter can be killed; break and replace the stall for a new one. He can't be leashed and doesn't ride, and one pushed more than 1.5 blocks from his spot is put back; his check of the stall doesn't load its chunk.
- The stall hires **foremen** only (builders are hired by a foreman). Anyone can hire from any stall. Right-clicking the recruiter opens the hiring screen: price ("Free in creative" for a creative player), an editable random name, and Hire. The new foreman appears in front of the counter (the first free spot of the two rows in front of it) and belongs to the payer. With no free spot the hire is refused, and payment is only taken once he has appeared; a builder hired from a foreman likewise needs a free spot next to him.
- A price of 0 (e.g. `foreman_cost_base = 0`) shows as "Free" and hires without paying.
- Prices (config) are paid in `hire_cost_item`, an item id or tag (default `#c:gems/emerald`). A foreman costs `foreman_cost_base` (20) plus `foreman_cost_step` (10) per foreman the player already has, capped by `max_foremen_per_player` (3, 0 = no cap). A builder costs `hire_cost_base` (10) plus `hire_cost_step` (5) per builder the player already has (orphans included), capped by `max_builders_per_player` (5, 0 = no cap). Ops summoning by command bypass the per-player caps but not `max_crew_size`. Prices are computed without overflow; one over 2147483647 can't be paid, and hiring says so and names the keys to lower.
- Commands: `/journeymen recruiter hire [name]` hires a foreman from the nearest recruiter (within 8 blocks) at the same price; `/journeymen stall place <pos> [facing]` (ops) places a stall without the item.

### Foreman screen

Right-clicking your foreman (owner or op) opens one screen with tabs:

- **Job:** with a job: file, phase, progress, what it's waiting for, and Cancel job (click twice). Without one: a schematic picker (server `schematics/`) with the material list, the `corner` and `allow-breaking-enchanted` options, and Place (starts placement mode).
- **Chests:** assigned supply and dump chests with remove buttons. Link mode: click "Link supply chests" or "Link dump chests", then right-click chests in the world (each click toggles; linked chests are outlined, supply green and dump orange). Right-clicking the foreman ends it and reopens his screen on the Chests tab; right-clicking another foreman ends it and opens his screen. It ends by itself after a minute without a click, at once when the foreman dies or is removed, and within a second when he unloads or isn't in the player's dimension; the client is told, so the outlines go.
- **Crew:** his builders with what each is doing, Hire builder (price, editable random name; the builder appears next to him; "Free in creative" for a creative player) and the owner's orphans with Adopt.
- **Orders:** follow / stay, rename, notices, dismiss (kill, with confirmation).

### Builder screen

Right-clicking your builder (owner or op) opens a screen with two tabs and its foreman's name:

- **Inventory:** its 27 slots and 4 armor slots, plus yours. Shift-clicking armor from your inventory puts it in the matching armor slot.
- **Orders:** follow / stay, rename, dismiss (kill, with confirmation).

The heavy screen actions are throttled per player: one request that loads a schematic (the Job tab's file info, check, start, Supply missing) at a time, and check, start and Supply missing each at most once a second. Extra requests are answered `Busy with your last request. Try again in a moment.`, not queued.

Every list that can scroll (schematic files, material list, chests, crew, the confirmation screen's pre-check result) shows a thin vanilla scrollbar when longer than its box; the wheel scrolls it, and the thumb can be dragged or the track clicked.

### Placement mode

Place (foreman's Job tab) closes the screen and shows a ghost preview (translucent blocks and the bounding box) at your crosshair. Sneak + scroll rotates, right-click confirms, sneak + right-click cancels. No item is involved. It stops when the server answers that the foreman is gone, when the player changes dimension and on disconnect.

Confirming opens a confirmation screen with the foreman's pre-check result (a result that arrives late only opens it while placement mode for that foreman and file is still on and no other screen is open, and only updates a confirmation screen for the same check; otherwise it is dropped) and Start (only when it passes), Move (back to placement) and Cancel. When the check finds unplaceable blocks or missing materials, a `skip-unplaceable` / `skip-missing` checkbox appears for each, and ticking one re-runs the check. A player in creative also gets "Supply missing (creative)" when materials or tools are missing: the server re-checks creative mode and command rights (no op needed: a creative player can take any item anyway), when the request arrives and again, looking the player up by UUID, once the schematic has loaded (a player who left creative, lost the rights or disconnected meanwhile gets nothing), supplies exactly what is missing like `foreman supply … missing-only` (supply chests first, then the player's inventory, all or nothing), re-runs the check and shows the outcome at the top of the result and in chat.

The server sends the schematic compressed (run-length encoded, deflated, packets of at most 512 KiB). The client builds the ghost once per rotation on a background thread (hidden faces culled), keeps it in a GPU vertex buffer and re-sorts it in the background. Schematics over 250,000 blocks, or whose ghost would need over 1,000,000 faces, show only their bounding box. Fluids and blocks drawn only by a block entity renderer (chests, signs, banners) don't show.

## Example schematics

`examples/schematics/` holds example schematics generated by `examples/make_schematics.py` (Python, no dependencies; byte-identical output when nothing changed). After changing the script, regenerate them and copy them into the dev run folders' `schematics/` (`neoforge/run`, `neoforge/run-tfc`, `fabric/runs/client`, `fabric/runs/server`). They are end-to-end cases: fill a foreman's chests with `foreman supply`, build, then `foreman check` should report 0 to place. `garden_shed.litematic` has two regions, one with a negative size; `old_hut.schematic` is a 1.12 MCEdit file with a WorldEdit offset and the block entities the 1.13 conversion needs; `uploaded/Steve/watchtower.nbt` sits in a subfolder like a Create upload; `tfc_farm.schem` is the TFC case.

## Roadmap

Phases 0–4 are built: the mod on both loaders, the builder entity, schematic loading, building by hand, and the survival UI. Phase 4's client side still has to be checked in game by a person.

Phase 5 built the shared work list: 5a ✅ the shared job model and pooled pre-check stock; 5b ✅ batch claims and item reservations, for clearing and placing. Both are kept and move to the foreman in phase 6.

Phase 6 is the foreman, replacing jobs and chests on builders (the old `builder build|check|cancel|chest|supply|join|leave` and comma-separated crews). There is no migration (the mod isn't released): builders drop old jobs and chest lists on load, keep their inventories and load as orphans.

- 6a ✅: the foreman entity, hiring (stall, `foreman hire`, `adopt`, summons), the foreman commands, jobs and chests on the foreman, builders as workers, `/journeymen notices`, old builder job/chest data and commands dropped.
- 6b ✅: the screens (foreman screen tabs, the slimmer builder screen, placement mode and the confirmation screen from the foreman).

Not tested yet (no way to test them so far):

- Other players hurting a journeyman when PvP is off (it should take no damage).
- A following journeyman getting unstuck towards its owner: the owner must be a real player in the player list, which a `debug as` fake player isn't. The same recovery is tested with `come`, chests, the site and `unstick`.
- Spawn protection and real claim mods (FTB Chunks, Open Parties and Claims, …) blocking the pre-check, the builders' breaking and placing, chest linking and stall placing. Claiming in FTB Chunks needs a real player in a team. The loader events themselves are tested with a simulated claim (`debug protect`, see `testing/README.md`).
- The survival UI by a person in game: the Inventory tab's slots and shift-click, armor rendering, link mode outlines, rotating with sneak + scroll, and using the screens with mouse and keyboard. Server side is tested with the debug commands; the foreman screen's four tabs, the builder screen's two tabs, the confirmation screen and the placement preview are rendered and screenshotted by the client test hooks.
- The progress bar of a real owner walking out of range: the suites see bars through `debug bars watch`, whose fake viewer is always in range.
- "Supply missing (creative)" for a player who disconnects while the schematic loads (fake players can't disconnect; leaving creative is tested).
- The placement preview with Sodium/Embeddium or Iris shader packs. It draws its own vertex buffer with the translucent block shader in the loader's after-translucent hook and uses no vanilla renderer internals, but nobody has looked.

Backlog: a hauler journeyman that carries materials for a crew, mirroring schematics, counting Unbreaking in the pre-check durability estimate, placing entities from schematics (item frames, paintings, armor stands), a job queue per foreman, an early have/need material check in the Job tab (design not decided).
